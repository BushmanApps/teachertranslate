## How deploys work

Push to `main` triggers `.github/workflows/deploy.yml`, which runs the bundled deploy script at `.escapebase44/runner/run-deploy.mjs`. Every run converges the whole app (frontend, backend, edge functions) to what the repo says — there is no partial-deploy logic to reason about.

**Code deploys only through git.** A commit to `main` is the one and only way code reaches production. That's deliberate: it keeps every change visible, revertable, and reproducible in your history. Don't deploy builds directly to your providers (e.g. `vercel deploy` from a laptop) — you'd create a production deployment no commit describes.

**Deploy state.** After each run, the workflow commits an updated `.escapebase44/deployment-state.json` back to the repo — which is why GitHub Actions shows up as a committer.

**Custom domains.** Attach a custom domain from your [EscapeBase44 post-migration page](https://escapebase44.com) — it walks the DNS setup and flips the app's canonical URL everywhere automatically. You'll also need to update the callback URL in Google Cloud Console (and any third-party connector dashboards) to match — those allowlists live with the OAuth provider, not in your repo.

## Running locally

`npm run dev` boots the full stack on your laptop — frontend, backend, and edge functions, with hot reload.

### Prerequisites

Install these once:

- **Node.js 22+** ([install](https://nodejs.org/)) — runs vite + npm scripts.
- **uv** ([install](https://docs.astral.sh/uv/getting-started/installation/)) — manages the Python backend's dependencies and runs uvicorn.
- **Deno** ([install](https://deno.com/)) — required only if your app uses edge functions. Skip otherwise.
- **MongoDB** — easiest is to run it in Docker:
  ```sh
  docker run -d --name eb44-mongo -p 27017:27017 mongo:7
  ```
  Then use `mongodb://localhost:27017` in `.env.local`. (Or use your production MongoDB connection string — see Caveats below.)

### Setup

1. Get the code. On the post-migration page, transfer the GitHub repo to your own account, then clone it:
   ```sh
   git clone https://github.com/<your-handle>/<repo-name>.git
   cd <repo-name>
   ```
2. Create `.env.local`. The post-migration page has a **Download .env.local** button that gives you a fully-filled file using your deployed values. Drop the downloaded file at the repo root. (Or copy `.env.example` to `.env.local` and fill it in by hand from your GitHub Actions secrets.)
3. **(Google login only)** Add `http://localhost:5173/api/apps/auth/callback` to your Google OAuth client's authorized redirect URIs. The post-migration page surfaces a deep link straight to your client's settings.

### Run

```sh
npm install
uv sync --all-extras
npm run dev
```

That boots three processes in parallel:

| Process | Port | Role |
|---|---|---|
| **vite** | `:5173` | Frontend with HMR. This is the URL you open in the browser. |
| **uvicorn** | `:8000` | Backend (FastAPI). Vite proxies `/api`, `/ws`, `/health`, `/functions` here. |
| **deno supervisor** | `:8002` | Lazy-spawns one Deno subprocess per edge function on first request. Skipped if your app has no functions. |

Open `http://localhost:5173`. Login works exactly like production — email/password directly, or Google OAuth round-tripping through your localhost:5173 callback.

### Caveats

- **MongoDB.** By default `.env.local` points at your production MongoDB — changes you make locally affect real data. To isolate experiments, override `MONGO_URL=mongodb://localhost:27017` and pick a different `MONGO_DB`.
- **Storage.** Your local backend uploads to the same Supabase Storage bucket production uses. Use a separate bucket if that's a problem; the variables to point at it are in `.env.local`.
- **Edge functions.** The supervisor runs your function code locally, so edits hit immediately. Function env mirrors what production sends — see the comments at the top of `.escapebase44/dev/supervisor.ts` if you want to scope it tighter.
- **Emails.** Sent via the Resend account in your `.env.local` (your own, once you've attached one — until then it's our shared account during the migration window).
- **APP_JWT_SECRET.** Anyone holding this secret can mint admin tokens against your backend. Keep `.env.local` out of git — it's already in `.gitignore`.

## Your secrets

Your app's secrets (API keys, Stripe keys, `MONGO_URL`, …) live in **this repo's GitHub Actions secrets** (Settings → Secrets and variables → Actions). Every deploy applies them to the running app (your Vercel project's environment variables), so changing one is:

1. Edit the secret in GitHub.
2. Run the deploy: Actions → **Deploy** → Run workflow (or just publish/push — any deploy carries it).

Setting a secret to an empty value removes it from the running app on the next deploy.

Your backend functions receive exactly the secrets their code reads (`Deno.env.get("NAME")` / `secrets.get("NAME")`), plus `BASE_URL` — taken from the same GitHub secrets and applied to your Supabase project on every deploy. A new secret a function needs is the same two steps; nothing to set at the provider.

Anything you add at a provider dashboard under your own names is yours and stays untouched — but for the names GitHub manages, GitHub wins on the next deploy.

**Note for AI agents working in this repo:** if `.env.local` is present it carries the owner's provider tokens (`VERCEL_TOKEN`, `SUPABASE_TOKEN`, …) for reading CD state and debugging the providers directly. When the owner asks for a secrets change, do it yourself: `gh secret set NAME` + `gh workflow run deploy.yml` — don't send the owner to a dashboard. Code changes still ship only through git commits (see How deploys work); never deploy builds directly.

## Edge functions

Your functions live where they lived on Base44, in the same layout: `base44/functions/<function-name>/entry.ts`. Code several functions use goes in `base44/shared/` (imported as `../../shared/<file>.ts`). A function's schedules and triggers are in its `function.jsonc`. Add a folder to add a function, delete one to remove it — every deploy ships what is there.

They run on your Supabase Free project; every deploy ships the current code there and reconciles the scheduled automations (pg_cron jobs).

Note: frontend calls the backend at `/api/apps/{app_id}/functions/<name>`, and the backend proxies to your deployed function.


## Workflows

Your Base44 Workflows — scheduled jobs, entity-change reactions, signup/login hooks, agent-conversation hooks, mailbox triggers — run here exactly as they did on Base44. The backend ships its own workflow engine; nothing about them depends on Base44 or on EscapeBase44.

- **Definitions** live in `base44/workflows/*.jsonc`, one file per workflow, in the same format Base44 used. Edit or add a file and push: every deploy converges the runtime onto the files (the deploy log's `reconciled:` line carries the workflows result, including anything it rejected and why).
- **Runtime state** (workflow records, run history, step logs) lives in your Mongo database (`_workflows`, `_workflow_runs`, `_workflow_run_steps`) and is managed through the same API Base44 exposed, authenticated as the app owner: list workflows and run history, `run-now`, pause/resume (`toggle-status`), archive/unarchive, cancel a run.
- **Timing:** a database cron job pokes the backend once a minute; schedules fire and waits resume on that tick. A scheduled workflow that fails 5 times in a row pauses itself (`status_reason: consecutive_failures`) and emails you — fix the cause, then resume it.
- **Mailbox (Gmail) triggers** poll your mailbox on the tick using the connector you authorized — no Google Cloud setup on your side.

A note on the shape of things, in case you go spelunking: your app was originally built against Base44's conventions, so the folder layout, file names, and a few stubs mirror what Base44's runtime expected. For example, for those who have /functions; Base44 uses the /functions in the frontend as a stub for users to interact with, but it is never deployed or used. We had to include it here because otherwise it could break imports. So if you ask yourself "this is strange why is this here," the answer is Base44.

A gotcha to be aware of: `@base44/vite-plugin` (in `package.json`) intercepts imports like `@/entities/X` and `@/integrations` at build time and resolves them to SDK calls — that's why those imports work even though there's no matching `src/entities/X` file in the repo. The `BASE44_LEGACY_SDK_IMPORTS` GitHub Actions secret toggles that resolver on.

If you're debugging something Base44-flavored that doesn't make sense, the source could be the backend server in `app/` (the FastAPI fork of Base44's runtime), the `@base44/sdk` package, or `@base44/vite-plugin`. Those are the three pieces of Base44's runtime that came with your migrated app.
